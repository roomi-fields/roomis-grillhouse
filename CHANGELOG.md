# Changelog

This file lists the notable changes of Roomi's Grillhouse, the frame itself. A project created by `grillhouse init` receives its own changelog, `templates/projet/CHANGELOG.md`.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the versions follow [Semantic Versioning](https://semver.org/) in 0.x: a change that obliges a project to act raises the minor, a fix the patch. One version covers the frame: it is the `version` of `packages/grillhouse/package.json`, which npm publishes with the frame's plugin, which takes it when the package is packed. A version is released per lot delivered to the projects, never per commit: its section is dated here and its commit tagged `v<version>`, whose push publishes the package (`CONTRIBUTING.md`, §5). The `version` of `package.json` (1.0.0) is the one a new project starts from, not a version of the frame.

### Added

- **The tools of the project enter the envelope** (grillhouse-4id): in SyntHub (SH-cgi.8, 2026-10-30), the tests of the pages need a Python with the site's packages, given by `SYNTHHUB_PYTHON` (installed under `~/.cache/synthhub-python`); the circuit's checks saw it, from the launcher's environment, but the developpeur's session did not: the envelope shows the home empty but what it declares and clears the environment, so « SYNTHHUB_PYTHON=… n'existe pas », and the developpeur could not play the tests he had to turn green. As Bazel declares what an action sees out of its sandbox (`--sandbox_add_mount_pair`) and the environment it gets (`--action_env`), a project declares its tools in `grillhouse.outils` of its package.json, `{ "<VARIABLE>": "<path>" }` (absolute or under `~`), read in one place, `scripts/outils-cles.mjs`. The envelope mounts each path read-only and passes each variable to the session; the circuit's passes (checks, final pass, regeneration of the references), `npm run verifier` and the night play with the same variables, taken from the key, whatever their launcher's environment. The key is read from the main tree, never a copy, so that an agent never opens a path for its next session; and a tool never undoes the envelope: a path is refused when it is `/`, the home or holds it, holds a mount of the envelope (the main tree and its copies, `/tmp`, `~/.claude`, the scratchpads, the npm cache, the session directories), or lies under a hidden directory of the first level of the home (`~/.ssh`, `~/.gnupg`…) but `~/.local` and `~/.cache`, or lies under or holds the keyrings `~/.local/share/keyrings`, a link judged by its target too — the review found that `"~"` brought back the whole home, credentials included, over the mounts in writing. A value that is not a string, an invalid variable name, a refused or missing path is refused by its name before any work: the circuit stops at « lancement », the envelope, `verifier` and the night refuse. The project's charter template names the key under « Commandes ».

## [0.16.0] - 2026-10-18

### Added

- **The meta-frame and the common charter**: `METACADRE.md` states the six intentions every rule serves and how a rule is written; `.claude/grillhouse/charte.md` holds the rules shared by every project, which each project's `CLAUDE.md` imports.
- **The grill**: the `grill` skill initialises a project (structural survey, owner's decisions, charter, architecture, frame, interfaces, lexicon) and settles every structure decision; a hook sends a structure question to it.
- **The roles**: the supervisor (`pitmaster`), the site manager (role 0), the explorer, the arbiter, the tester, the developer and the reviewer, each a project agent under its write locks (`scripts/verrous/`).
- **The tickets**: Beads holds the tickets; each ticket is created under its mother, carries numbered acceptance criteria and one delivery, and a hook refuses a second commit for a closed ticket.
- **The envelope**: a role agent works in a bubblewrap envelope that shows its component and only the published parts of the others (`scripts/enveloppe/`).
- **The controls**: the boundaries of the code (dependency-cruiser), the written interface against the code (API Extractor, TSDoc), the declared consumers of each interface, dead code (knip), out-of-frame packages, all played by `npm run grillhouse:gardes`.

- **The integration queue**: the integration commits a lot on its ticket's branch, and a queue brings the branch to main and reads the CI of the commit it pushes (`scripts/integration/`).
- **The circuit**: one command (`scripts/circuit.mjs`) leads each component of a ticket from the tester to the developer, then the reviewer, then the integration; a fresh site manager settles each stop.
- **The night**: `scripts/nuit.sh` plays every suite, the night tests and the time benches, and pushes its green commit to the night branch; a red night opens a ticket that names it.
- **The frame's update**: `npm run grillhouse:maj` brings a project's frame files (`.claude/grillhouse/fichiers.txt`) to Grillhouse's last version, with its hooks, scripts, plugins and generated files.
- **The board and the pane**: `npm run tableau` measures the project's state (chantiers, agents, tickets, working time); the Grillhouse mod shows it in a pane beside the transcript, and the status line shows the chantier in progress.
- **Shared submodules**: a working copy reads a submodule of the main repository, read-only (`grillhouse.partage`).
- **The version of the frame**: one version for the frame and its mod, in `.claude/grillhouse/VERSION`, which each project receives, so it knows the version it has; the mod's `plugin.json` carries the same, and a test refuses a gap. The report of `npm run grillhouse:maj` names it (« Cadre 0.16.0 (commit …) »).
