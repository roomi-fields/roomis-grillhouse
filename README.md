# Roomi's Grillhouse

**A ready-to-use project for working with Claude Code.** You create a project, open Claude Code
in it, and the session grills you on what the project must be — its goals, the mature products it
should measure itself against, its components and their interfaces. It then writes the project's
charter and reference documents, opens the first tickets, and runs the work through a supervisor
and fresh developer agents, each ticket reviewed before it closes.

The skills speak French.

**What every rule serves.** `METACADRE.md` (in the frame's plugin, `mods/grillhouse/`) fixes six intentions, and every rule of the framework
names the one it serves: a mature, professional product; the architecture decides and the code
follows; from the broadest to the most specific; proof before assertion; agents within a frame;
the owner settles what matters. It also fixes how a rule is written: positive, short, in the words
of whoever decided it, naming its intention.

**How decisions are arbitrated.** Every recommendation answers three questions, in order: what
does the mature reference of the domain do (a mature compiler, a professional DAW…); what already
exists and can be reused (standards, off-the-shelf tools, the author's own conventions); what does
the domain demand (e.g. speed for live coding). The project's answers live in its charter.

## 2. How it is built

Three layers, each with one job:

```
┌─ Claude Code layer ────────────────────────────────────────────────────────────┐
│ .claude/settings.json   plugins (grillhouse, mattpocock-skills, rtfm),         │
│                         permissions                                            │
│ .mcp.json               the CodeGraph server                                   │
│ plugin grillhouse       the brigade (below), the seven roles under their       │
│                         write locks, the hooks, the common charter             │
│ grillhouse session-start   hook: what is still empty → propose the grill       │
│ grillhouse structure-guard hook: a structure question → the grill              │
├─ Project knowledge ────────────────────────────────────────────────────────────┤
│ METACADRE.md (plugin)   the six intentions every rule serves, how rules are    │
│                         written (fixed by the framework)                       │
│ CLAUDE.md               the project's charter: owner, what decides, how we     │
│                         arbitrate, the commands; imports the common charter    │
│ .claude/grillhouse/     the common charter: the task flow and the frame's      │
│   charte.md             rules, the same in every project (fixed by framework)  │
│ docs/ARCHITECTURE.md    how it is built, and why        (written by the grill) │
│ docs/CADRE.md           each component's role and boundary (R1…)               │
│ docs/INTERFACE.md       what crosses each boundary, and the guard that holds it│
│ CONTEXT.md              the domain lexicon                                     │
│ docs/agents/issue-tracker.md   ticket conventions                              │
│ pitmaster/SUIVI.md      the supervisor's follow-up: open questions, last round │
├─ Code tooling ─────────────────────────────────────────────────────────────────┤
│ packages/grillhouse/     the frame's command, `grillhouse <sous-commande>`,    │
│                          its scripts and its tests (an npm package)            │
│ templates/projet/        a new project's src/ tests/: TypeScript or JavaScript │
│ ESLint, Prettier, EditorConfig, tsconfig, GitHub CI and release workflows      │
│ templates/projet/deployment/, ecosystem.config.cjs, .env.example: services     │
└────────────────────────────────────────────────────────────────────────────────┘
```

**The brigade** — each skill named after its role first:

| Role                          | Skill          | What it does                                                                                                                          |
| ----------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Initialisation & architecture | `grill`        | Surveys the code, grills the owner, writes the charter and reference documents.                                                       |
| Supervisor                    | `pitmaster`    | Keeps the tickets, hands each one to a fresh agent, reviews closures, keeps the frame.                                                |
| Testwriter (agent)            | `testwriter`   | Writes a ticket's tests from the spec, before the code; writes test files and the shared test material only.                          |
| Developer (agent)             | `developpeur`  | Makes those tests pass; touches no test nor the shared test material, writes no code before the ticket's Architecture section.        |
| Reviewer (agent)              | `relecteur`    | Reviews the lot adversarially (edge cases, verification gaps, the frame); writes nothing.                                             |
| Questioner (agent)            | `questionneur` | Questions a proposal it did not write (a ticket's plan, the supervisor's), led by the frame, no set list; decides and writes nothing. |
| Explorer (agent)              | `explorateur`  | Writes a ticket's plan at step 1 and answers the questioner once; runs an exploration ticket. Writes no code.                         |
| Measurement                   | `mesure`       | Measures without fooling itself; proves a guard bites before calling it green.                                                        |
| Writer                        | `redacteur`    | Writes human-read documents (architecture on the arc42/C4 model, frame, interface).                                                   |
| Release                       | `release`      | Bumps the version, updates the changelog, tags, publishes.                                                                            |

A change of behaviour is one ticket that passes from agent to agent in its copy: tests (testwriter) →
code (developer) → review → commit on the ticket's branch → the queue brings it onto main, which closes it.
As a merge request, the ticket has one author per step: one testwriter and one developer for the whole ticket,
each in the envelope of every package of its plan, then a final pass and a review on the whole; no component is
a unit of the circuit.
The supervisor launches the ticket's circuit (`packages/grillhouse/scripts/circuit.mjs`) once. As a CI applies its
rules without asking and calls a person only for what no rule settles, the circuit makes the mechanical gestures
itself, with no session, each written at the ticket and in the log with its rule (`GESTES` of
`packages/grillhouse/scripts/etapes.mjs`): a command at 75 played once more, the end at 75 (« à repasser »), a
developer's sending to the testwriter, the regeneration of the references, a developer with nothing to deliver judged by
the checks. Every other stop ends the circuit on a question for
the supervisor, with its exit code: the circuit's state carries the fact, its piece (file:line, or command and output),
the question and who must answer it (`superviseur`, or `responsable` for the reviewer's question on a real word of the
language). The supervisor answers by a command of the circuit, `--reprendre` (with `--contexte`) or
`--depuis <testwriter|developpeur>` (the whole ticket again from that step), `--etendre <paquet>` (the plan gains that
package, before its first reader, then the step under way resumes), or `--arreter` (its motive in `--contexte`), and carries to the
owner what is his; a decision of the owner that changes the plan enters the ticket's description, which every agent
reads. So the supervisor is woken only by a lot integrated or by a question no rule settles.
Before the first testwriter, the plan (1 Plan), as an RFC: the explorer (`explorateur`) writes it after surveying the
components the ticket reaches (`packages/grillhouse/scripts/composants-affectes.mjs`: each element's provider and readers,
by the names, by TypeScript's language service, by the paths their tests declare they read (`grillhouse.lit`) and by the
Rend of the components' CADRE.md; a package that carries a type without reading it is no reader, and a symbol internal
to a package has none out of it): its sheet carries the criteria, the packages to touch and its open questions, which
the circuit writes at the ticket, the packages at the end of its title, the list every later session's envelope
writes. The questioner (`questionneur`) reads the plan once, as Amazon's bar raiser or a cockpit's challenge and
response; the explorer answers once, CHANGE or GARDE by question, its session resumed; what stays open goes up to the
supervisor (`questionnement`, 22), who changes the plan or keeps it, then `--reprendre` lets it pass. The supervisor
has his own plan questioned by the same agent before he gives it to the owner.
Each session writes at the ticket under its role as author (`BEADS_ACTOR`, which it may not change),
the circuit's own lines under `circuit`, the queue's under `file`, and the reviewer's verdict under
`relecteur`, written by the circuit from the reviewer's sheet. Each session's instruction carries the ticket's
description as it is at its launch, the ticket's notes when it has some, the reviewer's findings still open, and the
last handover of its own role (for a developer who has none yet, that of the testwriter); the reviewer's carries no
criteria, only the path of the claims file that holds them. A finding of the reviewer goes straight to the agent it
names and stays open across every relaunch, as an unresolved thread of a review, until the reviewer judges it lifted
or accepts the lot. The circuit gives the reviewer the mechanical list of every element the lot adds, changes or
removes (function, class, type, interface, constant at the top, export, each with its package and its file:line,
`packages/grillhouse/scripts/langages/typescript/elements-du-lot.mjs`), and the reviewer's sheet gives one line of conformity per element,
conforming or not, the rule cited (CADRE, INTERFACE or ARCHITECTURE; a new export, its entry in the INTERFACE): a « non »
sends the lot back, an element without its line refuses the sheet.
Each session of a testwriter, a developer, the reviewer and the questioner ends on its sheet, the structured
output its role's schema describes (`claude -p --output-format json --json-schema`, `packages/grillhouse/scripts/resultats.mjs`):
the circuit decides on it, and on the summaries of Turborepo, the JSON reports of Vitest and the SARIF of
the guards, never on free text; a session without a sheet that conforms is resumed once, then the circuit
stops (`sans-fiche`). A developer who leaves a red in the tests of the lot sends it to the testwriter (`renvoi`
in its sheet), and a plan without tests goes straight to the developer. A sheet of a testwriter or a
developer carries its status, FAIT, BLOQUÉ with its reason or BESOIN with its question: a BESOIN, or a
BLOQUÉ that sends the red to no testwriter, stops the circuit at once (`besoin`, `hors-portee`), a question for the
supervisor, the agent not relaunched on that red.
A relaunch of a testwriter or a developer on its step (after a refused proof, after red checks) resumes its
session (`claude --resume`) with a short instruction, the new report alone; the last attempt is a fresh
and whole session, and so is a resumption that fails.
The locks are hooks in the settings of each role's session (`packages/grillhouse/scripts/verrous/`, given by
`packages/grillhouse/scripts/droits.mjs` with the rights its skill names, the user's own configuration left out), so
an agent cannot aim the code at its own tests, nor edit a file by the shell; the integration sorts the lots by the same rule (the tests lot holds the
testwriter's files, the code lot none of them). Each agent runs as a fresh session inside the **envelope** of its plan
(`packages/grillhouse/scripts/enveloppe/`, a bubblewrap sandbox): it reads the whole copy, its indexes included,
and writes only the packages its ticket's plan names; a write out of the plan stops the session, and the
supervisor extends the plan or refuses. The package of the shared test material (the package that exports
`./test-fixtures`) is written by the testwriter alone. Of the home and
the session directory it shows only what it declares (claude, node, git, the session's tools and
the repository), and of the environment only what it declares (the base of a login session and
claude's own variables), in a process space of its own. So of the machine's credentials only
claude's own are reachable (`~/.claude`, a throwaway copy of `~/.claude.json`, its API key or OAuth
token), and no socket of the session, no token held in a variable (`GH_TOKEN`…). A missing piece
of data becomes a request to the component that provides it, not a local recomputation. One
ticket makes one delivery: a goal of unknown size starts with an exploration ticket, every ticket
is created under its mother (numbered `320.2.1`) and every ticket stands at one step of the tree of its circuit (`packages/grillhouse/scripts/etapes.mjs`: 1 Plan; 2 Tests, 2.1 Preuve du rouge; 3 Code, 3.1 Contrôles; 4 Passe finale et relecture, its sub-steps 4.1 Passe finale, 4.2 Régénération des références and 4.3 Relecture; 5 Intégration, its sub-steps 5.1 Commit and 5.2 File : main, poussée, CI), each step carrying its bounded loops (`essai 2/3`, `tour 2/3`), and a hook refuses a second commit for a closed ticket (a reopened ticket takes correction commits).

**The board** — the `grillhouse` mod (a Claude Code plugin whose source lives in `mods/grillhouse`, carried
by the package `@roomi-fields/grillhouse`, whose root is the plugin, listed by the marketplace roomi-fields as `grillhouse@roomi-fields`,
enabled in each project's settings) shows, measured and never declared, in the `/grillhouse` pane, three levels: the project (its work tickets by state, the
agents' time and tokens of the day and in all, the alerts); the agents: the tree of the steps, as a pipeline
of GitLab CI shows its stages, each step on its line « number · title · who », a step with sub-steps folded
(`▸ 4 · Passe finale et relecture`) while none of them holds a ticket and unfolded (`▾`) once one does, its empty sub-steps
dimmed, an empty step dimmed, where each ticket stands on one line, once — a ticket with a circuit
(`packages/grillhouse/scripts/circuit.mjs`, read in its state file) at the step of its state, its subject, the counters of its step's
bounded loops from their second pass (`essai 2/3`, `tour 2/3`), at an automatic step the
progress of its pass in figures, as Bazel counts its actions (`87/123 · il y a 8 s`: the test files done over
planned, a file replayed from Turborepo's cache counted done, and the time since the last sign;
`⚠ figée 12 min · 87/123` in red past 5 min; at 5.2 the steps of the CI;
`packages/grillhouse/scripts/avancement.mjs`), or, stopped on a question, under its step after a line
« ⤷ Question · superviseur » (« ⤷ Question · responsable » for a question the owner must answer), its card
opening on that question, or on where it stopped and why, and its line ending on its ticket's
time and tokens; any other ticket at the step of the agent that runs on it, or waiting at the step of the
next role of the flow; at the head of AGENTS, a measure out of a ticket that holds the lock of the machine
(`⏳ Mesure · Grillhouse · npm run verifier · 51/123 · il y a 3 s`, a supervisor's or an integration's);
the chantier in progress, its tree of
mother tickets with each one's work done over all; then the tickets closed today. Every line of each list
shows, and the wheel scrolls the pane; `g` fills the pane with the chosen ticket's whole text, which the
arrows, the page keys and the wheel scroll, and `g` again brings the board back. A finished agent is read from the
register its end writes (`packages/grillhouse/scripts/registre.mjs`: the hook ends at once and a detached process
reads the transcript in chunks and writes the line, once per stop; the launcher of a role agent writes its
line again from outside the envelope once it ends, `--copie`; `--rattraper` adds the agents that ended
before it), a running one from its transcript, those launched
in a shell included; a ticket's time adds the steps its circuit leads itself (the proof, the checks, the
final pass, the integration, the queue), which the circuit writes to the same register, each instant once.
The card of a ticket whose circuit ended opens on the key figures of its bilan (`packages/grillhouse/scripts/bilan.mjs`): wall
time, share lost, sessions, cost.
Without the mod, `npm run tableau` prints the same lines. The status line
(`packages/grillhouse/scripts/ligne-etat/`, the project's `statusLine`) keeps the person's own status line on the
left, or a default one (model, context, rate limits), and shows the chantier in progress on the
right, as each measure writes it to `grillhouse-etat.txt` in the common git directory.
The pane docks beside the transcript in Claude Code's fullscreen layout (`/tui fullscreen`, from
110 columns); the wheel scrolls the transcript there only while Claude Code captures the mouse, so
`CLAUDE_CODE_DISABLE_MOUSE` stays unset (`CLAUDE_CODE_DISABLE_MOUSE_CLICKS` keeps the wheel).

The full file tree is in [STRUCTURE.md](STRUCTURE.md).

## 4. Start

```bash
git clone https://github.com/roomi-fields/roomis-grillhouse
cd roomis-grillhouse
npx @roomi-fields/grillhouse init ~/dev/my-project [ticket-prefix]
cd ~/dev/my-project && claude
```

Requirements: Linux with Bubblewrap (`bwrap`, the envelope each role agent runs in: `sudo apt install bubblewrap`), Node.js ≥ 22, git, Claude Code; a session start names Bubblewrap under « Manque » while it is absent. Everything else installs by default: `init`
installs Beads and CodeGraph and indexes the code, places the git hooks, and installs the plugins
`.claude/settings.json` declares, for the project (and `npm run grillhouse:maj` installs the plugins too); a session start names under « Manque » each plugin still missing. An existing project adopts Grillhouse by copying the template files into it and running
`npm install -D @roomi-fields/grillhouse`, then `npx grillhouse maj`. MIT licence.
